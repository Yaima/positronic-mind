# Project instructions

Read `docs/pipeline/PROCESS.md` before any pipeline work.

## Repo facts

- Stack: Python 3.11+, package `positronic_mind` under `src/` (setuptools, `pyproject.toml`). Tests: pytest. Lint: ruff. Types: mypy strict. No DB, queues, or API layer yet (Phase 0).
- Layout: `src/positronic_mind/` with one subpackage per layer: `workspace/` (global workspace, salience, controller), `modules/` (faculty modules), `conscience/` (principle check), `veto/` (Cedar rules, AgentTrust ID bridge), `trace/` (decision event schema), `memory/` (episodes, graph, consolidation), `reader/` (web reading). `tests/` is flat (one file so far; it will mirror `src/` as layers gain code). `eval/suite/` is reserved for the 50-task baseline and `eval/experiments/` for experiment runs; both hold only `.gitkeep` today. `values/values.example.md` is a fictional sample ledger; `values/values.md` is instance data and gitignored. `docs/proposal.md` is the design; `docs/research-review.md` the evidence; `docs/decisions.md` the decision log. No entry point yet.
- DB: none yet. Phase 2 adds a SQLite or Markdown episode store and a property graph; schema in `docs/proposal.md` (Semantic memory schema).
- Base branch: main. Hosted on GitHub (Yaima/positronic-mind); PRs via gh, merged by humans.
- Tests: `python -m pytest -q` from the repo root with the venv active (`python -m venv .venv && source .venv/bin/activate && pip install -e ".[dev]"`). Nothing else needs to be running.
- Lint: `python -m ruff check src tests`; `python -m mypy` (config in pyproject.toml, strict, package positronic_mind); `python -m pip_audit` for security.
- Private deps / credentials: none. Instance data (values, memory, trace, models) is gitignored and never committed.
- Design constraints every agent follows: the model check in the veto may only make a decision stricter, never widen a rule's deny; every side-effecting action records a decision event; instance data stays out of the repo. See `docs/proposal.md`.
- Ticket and branch: set per feature in `docs/features/<slug>/state.json`

## Feature pipeline

Read `docs/pipeline/PROCESS.md` before any pipeline work. Every feature lives in `docs/features/<slug>/`; read its `state.json` before touching it. Stages are skills in `.agents/skills/` (also `.claude/skills/`), invoked as slash commands with the slug as the first argument:

| stage | what it does |
|---|---|
| `/start` | Role-aware entry point. Reads the operator's role from docs/pipeline/pipeline.local.json, lists features waiting on that role, and offers the next action. Usage: /start [slug] |
| `/codebase-map` | Regenerate docs/pipeline/CODEBASE.md, a map of the real repository (layers, entry points, conventions, test layout, commands) built from files on disk. Agents read it at the start of every run. Run after adopting the pipeline and whenever structure changes. |
| `/grill` | Interview the user about an idea until requirements, scope, and terminology are pinned down, then record decisions. Run before /prd. Usage: /grill <slug> <one-line idea> |
| `/estimate` | Expected effort and worst case (named risks, triggers, cost) for a ticket, calibrated on past features in this repo, compared with the ticket's own points. Optional, any time after ticket.md exists. Usage: /estimate <slug> |
| `/prd` | Write the PRD for a feature from the grill decisions (or a raw idea) with numbered testable requirements. Usage: /prd <slug> [idea] |
| `/handoff` | Engineering handoff. Reviews the PRD against the codebase, then produces spec, data model (if data changes), and a tracer-bullet task list. Usage: /handoff <slug> |
| `/implement` | Run the TDD loop over tasks.md, one task at a time, test-writer then implementer, until every task is checked off. Usage: /implement <slug> [task-id] |
| `/review` | Independent code review loop. code-reviewer reviews the branch; on CHANGES_REQUESTED the implementer fixes blockers/majors and the review reruns, up to max_review_rounds. High blast-radius features get a second, separate review pass. Usage: /review <slug> |
| `/qa` | Acceptance testing per PRD requirement on an approved branch, then open the PR for human merge. Usage: /qa <slug> |
| `/feature` | Run the whole pipeline for one feature, resuming from whatever stage state.json says. Stops at every human gate. Add --lite for small changes (skips grill, PRD, and data model; keeps tests, review, and the merge guard). Usage: /feature <slug> [--lite] [idea] |
| `/roadmap` | For work too big for one feature. Splits an initiative into feature slugs with dependencies and writes docs/roadmaps/<name>.md; each slug then runs through /feature on its own. Usage: /roadmap <name> <description> |
| `/retro` | After a feature ships, propose edits to rules, agents, and CLAUDE.md from what went wrong in its review and QA. Usage: /retro <slug> |

Roles run in a fresh context with only the inputs the stage lists (`docs/pipeline/RUNNING-ROLES.md`). They are subagents in `.claude/agents/` (Claude Code, Copilot), `.codex/agents/` (Codex), `.gemini/agents/` (Gemini):

| role | job |
|---|---|
| `architect` | Writes the technical spec, data-model.md when the data model changes, and the ordered task list from a reviewed PRD. Use for engineering handoff. |
| `code-reviewer` | Independent review of a feature branch against its PRD and spec. Reads the diff, runs the tests itself, checks requirement coverage and security, and issues a VERDICT. Never reads the implementer's notes. Use after implementation and after each fix round. |
| `estimator` | Estimates real effort and the worst case for a ticket from the code it touches and from past features in this repo. Use any time after `ticket.md` exists; rerun after grill or handoff for a tighter number. |
| `implementer` | Implements one task from tasks.md to make its failing tests pass, or fixes blocker/major findings from a review round. Edits source files only; test files and CI/lint config are read-only (enforced; see ENFORCEMENT.md). |
| `product-manager` | Turns an idea into a PRD with numbered, testable requirements. Use at the start of a feature or when requirements are vague. |
| `qa-engineer` | Writes and runs acceptance tests per PRD requirement on an approved branch, black-box where possible. Use after code review approves. |
| `requirements-analyst` | Checks a PRD against the real codebase for feasibility, conflicts, gaps, and reuse. Use after a PRD exists and before any design or code. |
| `retro` | After a feature ships, reads its review-log, qa-report, and agent-runs.log and proposes edits to rules, agents, and CLAUDE.md so the same mistakes are not repeated. Proposes; the user applies. |
| `test-writer` | Writes failing tests for one task from tasks.md, using the repo's existing test conventions. Edits test files only. |

Commit, push, and merge are human actions (`commit_mode: human` in `docs/pipeline/pipeline.json`). Agents leave changes in the working tree and end their report with `git status --short`. What each tool enforces vs. asks: `docs/pipeline/ENFORCEMENT.md`.

## Pipeline rules

Five lines every agent follows on every turn:

- Read the code; never recall it. Cite `path:line` for any claim about the repo, and end every report with `## Evidence` (files read, commands with exit codes, things looked for and not found).
- `docs/features/<slug>/ticket.md` is the scope authority. Behavior the ticket does not ask for is an `[ADDS SCOPE]` question for the human, never a default.
- A task starts with a failing test. Test files are read-only for the implementer; a wrong test is a dispute in `tasks.md`, never an edit.
- The reviewer runs the tests itself and reads no implementer notes. Only `code-reviewer` writes a `VERDICT:` line.
- Commit, push, and merge are human actions in `commit_mode: human`. Leave changes in the working tree and end with `git status --short`.

The full rules, loaded by the stages and roles that cite them:

- `docs/pipeline/rules/git.md`: Git rules
- `docs/pipeline/rules/grounding.md`: Grounding: read the code, never recall it
- `docs/pipeline/rules/review-standards.md`: Review standards
- `docs/pipeline/rules/roles.md`: Operator roles and gate ownership
- `docs/pipeline/rules/scope.md`: Scope rules (always on)
- `docs/pipeline/rules/tdd.md`: TDD rules
